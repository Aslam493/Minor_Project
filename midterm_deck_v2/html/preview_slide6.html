AFTER BOOT
After Boot, What We Actually Do
Once the boot chain finishes, this is the runtime loop that runs continuously on Core1.
SECURE WORLD (CORE1) — AUTOMATIC FIQ PATH
1
Core1 stays in Secure World
rpi3_can_server_loop() runs continuously inside OP-TEE on Core1 - it never returns to Linux.
HARDWARE-PROVEN
↓
2
A CAN frame arrives
MCP2518FD (SPI0) → GPIO25 → BCM2837 interrupt routing → Secure FIQ, delivered straight to Core1.
HARDWARE-PROVEN
↓
3
Core1 validates the frame
CAN ID check, replay/counter check, and timestamp check all run on the real captured frame.
HARDWARE-PROVEN
↓
4
Core1 makes the Accept / Drop decision
HMAC authentication is part of the design but is currently blocked - the demo skips this stage.
BLOCKED
NORMAL WORLD (CORE0 / CORE2 / CORE3) — RUNS IN PARALLEL
5
Linux keeps running on Core0, Core2, Core3
The whole time, Linux carries on normally - it never binds a CAN driver and never sees this happen.
HARDWARE-PROVEN
6
Userspace can separately probe OP-TEE
spi_poc_test / secure_can_demo issue their own SMC calls - a control path, separate from the FIQ loop.
IMPLEMENTED
This loop runs continuously and automatically - independent of whatever Linux is doing on the other cores.
