# FINAL TEST REPORT: Secure CAN Monitor, Raspberry Pi 3 B, Mode P (2026-11-22)

**Summary: 30 PASS / 1 FAIL / 10 documented limits**

FAIL cases: E2b. Each FAIL is explained below; nothing was changed to turn it into a PASS.

## PACKET_LOSS_VERDICT
> **0 loss up to 640 frames/s sustained and for any single burst up to about 2,490 frames at the full bus rate of 3,587 frames/s; above that, every lost frame is lost at ONE stage, the forwarder's Mode P queue (2,048 frames; current overload policy: the OLDEST frame is dropped and counted) and not at the socket buffer and equals the Secure World's counter gap exactly. Real socket buffer: 8,388,608 bytes granted to the forwarder's socket (4,194,304 requested; the kernel doubles it), about 9,380 frames at 894 bytes per frame (derived from the measured 238 frames at 212,992 bytes); the kernel socket buffer, the chip FIFO (20 entries), the sender queue (2,000) and the forwarder read loop dropped nothing at any rate up to the bus maximum. The overflow stage is NOT the socket buffer.**

Evidence: D1-D5 (273,000+ frames, 18 of 18 runs with the exact Secure World gap accounting: sent = judged + sender give-ups + chip loss + kernel socket drops + forwarder-rejected + Mode P queue drops, and the Secure World counter span minus its advancing frames plus the tail equals the counted drops), `REAL_BUS_RESULTS.md` section 10.10.

5. The heartbeat log holds 6,000 records (about 300 s), so for the 320 s run it shows 311 answers while the forwarder's own counter shows 321; both are on time.
