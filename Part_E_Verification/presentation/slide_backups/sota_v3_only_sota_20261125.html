Secure CAN Monitor · Raspberry Pi 3 · OP-TEE

State of the art, from my design notes. AUTOSAR SecOC adds counter-based freshness against replay on CAN: I use the same counter idea in the Secure World. TEECheck, from RTNS 2020, uses a trusted execution environment to vet outgoing CAN frames at the source, on a Cortex-M: that is prevention, while my monitor only detects. iCORE, from SAC 2019, diverts a core into the Secure World at boot, so it runs as a master and does not wait for Linux to call it; my core 1 uses this mechanism. EmLog, from 2017, is tamper-resistant logging on OP-TEE, with forward integrity and resistance to truncation and re-ordering; it is the model for the secure log I want to build next. Also in my notes: Schneier and Kelsey, 1998, HMAC hash chains for logs, which do not catch cutting off the end; SPROBES and TZ-RKP, which are prevention-oriented and invasive to Linux. The gap: I found no work that pairs OP-TEE with detecting CAN attacks when Linux itself is compromised, and that is what this project addresses. The promises made at midterm are not on this slide. They were: HMAC authentication (done), reduce validation latency (done), store validated packets in flash memory (not built, designed), rate and flood detection (partly: every drop counted, no flood alarm), and an end-to-end demo with real measurements (done).
