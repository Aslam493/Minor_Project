Secure CAN Monitor · Raspberry Pi 3 · OP-TEE

Left: related work, taken from my design notes. AUTOSAR SecOC adds counter-based freshness against replay on CAN. TEECheck, from RTNS 2020, uses a trusted execution environment to vet outgoing CAN frames at the source: that is prevention, on a Cortex-M. iCORE, from SAC 2019, diverts a core into the Secure World at boot so it runs without waiting for Linux to call it; my core 1 uses the same mechanism. EmLog, from 2017, is tamper-resistant logging on OP-TEE; it is the model for the secure log I want to build next. Schneier and Kelsey, 1998, describe HMAC hash chains for logs. The gap: I found no work that pairs OP-TEE with detecting CAN attacks when Linux itself is compromised, and that is what this project addresses. Right: the five items promised at midterm, in the midterm's own words. HMAC authentication and lower validation latency are done. Rate and flood detection is partly done: every dropped frame is counted exactly, but there is no separate flood alarm. Storing validated packets in flash is not built; it is designed, and it is the first item of future work. The end-to-end demo with real measurements is done: all 32 test cases pass, 31 the first time and one, the forwarder starting at boot (E2b), after a fix; one new limit was found after the fix (E2c).
