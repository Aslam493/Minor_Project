Secure CAN Monitor · Raspberry Pi 3 · OP-TEE

At midterm HMAC was listed as blocked. Measuring showed the whole Secure World was slow: 4.0 ms plus 4.95 ms per frame at 600 MHz, so only about 7 frames fit in one 40 ms answer, and a 1,004-frame burst took 9.9 seconds, about 101 frames per second. Step 2: doubling the clock to 1200 MHz made it 4.6 times faster per frame, which was a clue, but one HMAC still took about a millisecond, far too slow for the work, so the clock was not the cause. Step 3: the cause was a debug option, CFG_CORE_DEBUG_CHECK_STACKS, which compiles the whole core with instrumentation: 5,060 hook calls, so every call into the core was 45 to 100 times slower. Step 4: removing that one flag, with the same source, gives 54.6 microseconds per frame, 32 frames use under 2 ms of each 50 ms period, and the measured burst takes 1.56 seconds. After the fix the clock no longer matters: 1.57 seconds at 600 MHz and 1.56 seconds at 1200 MHz. The same debug option was in the core built on 20 September, the one in use at midterm: its binary contains the stack-check hook functions, while the 30 August core does not. That is the likely reason HMAC looked too slow at midterm; the confirmed measurements are from November. The before-fix figures 9.9 s and 101 frames per second were measured; the 7 frames is calculated from the 40 ms deadline.
