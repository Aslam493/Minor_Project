Secure CAN Monitor · Raspberry Pi 3 · OP-TEE

Motivation and state of the art on one slide. Left, the problem. Picture a car: the brakes, the engine and the steering are separate small computers, called ECUs, on one shared wire, the CAN bus. A CAN frame carries no proof of who sent it, so anyone who gets onto the bus, the attacker in red, can send a forged frame. Problem one: anyone can send a frame, which allows a spoofed ID, tampered data, a replay of an old frame, or silence. Problem two: the check on those frames runs in Linux, and a compromised Linux can accept forged frames or hide them. Problem three: the record of what happened can be rewritten afterwards; that one is future work. Right, what exists, from my design notes. AUTOSAR SecOC adds counter-based freshness against replay on CAN; I use the same counter idea in the Secure World. TEECheck, RTNS 2020, uses a trusted execution environment to vet outgoing CAN frames at the source on a Cortex-M: that is prevention, while my monitor only detects. iCORE, SAC 2019, diverts a core into the Secure World at boot, so it runs without waiting for Linux; my core 1 uses this mechanism. EmLog, 2017, is tamper-resistant logging on OP-TEE; it is the model for the secure log I want to build next. Also in my notes: Schneier and Kelsey 1998, HMAC hash chains for logs; and SPROBES and TZ-RKP, which are prevention-oriented and invasive to Linux. The gap: I found no work that pairs OP-TEE with detecting CAN attacks when Linux itself is compromised. The goal of this project is to detect these attacks from the Secure World, where Linux cannot hide them. The five promises made at midterm are not on this slide: HMAC authentication (done), reduce validation latency (done), store validated packets in flash memory (not built, designed), rate and flood detection (partly), end-to-end demo with real measurements (done).
