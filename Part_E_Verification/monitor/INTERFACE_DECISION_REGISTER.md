## Inconsistencies found in the existing documents while building this register (need your ruling)

1. **Command 23 versus the integration matrix.** The matrix (section 4i) and the earlier contract say cmd 23 recomputes the expected nonce with HMAC outside the lock. But the nonce is stored once cmd 22 has derived it (G6: `hb_nonce`, `hb_nonce_valid`). An answer for a nonce that was never fetched cannot be legitimate. A plain compare against the stored value needs no HMAC and one hold. See DEC-IF-7.
2. **Acknowledgement versus the lost counter.** G8 says pinned entries are exempt from `ev_ack`, but nothing says what acknowledging an ordinary entry changes. As modelled, overwriting an acknowledged entry still increments `ev_lost`. See DEC-IF-4.
3. **Timing constants differ between documents.** The design document and model use T = 50 ms and H = 500 ms; the design report (`aslam_designattuesday.md`) uses a traffic timeout of 300 ms, H = 1 s, D = 3 s and a boot grace G = 60 s. See DEC-IF-11.

4. **Evidence-class floods by a caller with no key (flagged 2026-11-07).** The design says (O-07) that a caller with no key must not be able to fill the evidence ring, but AUTH_FAIL is listed as an evidence class, and any caller can create AUTH_FAIL events by submitting a bad tag (REPLAY events likewise, using any frame captured from the bus). Evidence classes are never rate limited, so after their 4 pinned slots such a flood can evict other, older, unpinned unread evidence. The pinned quota still protects the first 4 events of every class. Resolve in DEC-IF-10 (for example: after the pinned quota, further AUTH_FAIL or REPLAY events update the exact counter and a per-class rate-limited event only).

## Detail

### DEC-IF-1 Health pair (Step 3; DECIDED 2026-11-07, approved as proposed)
Slots 2 and 3 are `VALUE_OUTPUT` in every command; the full `param_types` table is in the session record. Content (lock-free and constant data only, so it can be filled on `BUSY`): `p2.a` = Core 1 poll age in ms (`0xFFFFFFFF` = never polled or 49 days or more); `p2.b` bit 0 = `starved`, bit 1 = `init_ok`, bits 8 to 15 = `skip_count` saturated at 255, other bits zero; `p3.a` = `pta_lock_timeouts`; `p3.b` = `skip_total`. Filled on `TEE_SUCCESS` and `TEE_ERROR_BUSY`, zero for every other result. Read after the final unlock or unmask. "Lease active" and a "this is BUSY" bit were removed (lock-protected / redundant).

### DEC-IF-2 Unknown-command dispatch (DECIDED 2026-11-07, Option A)
Source today: early `if` blocks for ids 4, 15, 16, 6, 14, 7, then the shared type check (exactly `(VALUE_OUTPUT, NONE, NONE, NONE)`), then a `switch` whose `default` is `NOT_SUPPORTED`.
Decision: in builds with `CFG_RPI3_CAN_MONITOR=y` the dispatch order is (1) id not in the known set (0 to 16 plus 17 to 23) returns `NOT_SUPPORTED` before any parameter check; (2) hardened profile and a refused legacy id returns `NOT_SUPPORTED` before any parameter check, with a best-effort event; (3) ids 17 to 23 go to the monitor handler (own exact `param_types`, then `init_ok`, then the command sequence); (4) everything else takes the legacy path unchanged. **In the disabled build nothing changes** (17 to 23 fall through the legacy path as today). If monitor init fails, only 17 to 23 return `BAD_STATE`; legacy commands (including 1, 2, 12 used by `verify_boot`) keep working.
Existing expectations kept: wrong types on a known command is `BAD_PARAMETERS`; an unknown id with `VALUE_OUTPUT` is `NOT_SUPPORTED` (`ta_roundtrip`).
Checks: DS1 unknown id with any types is `NOT_SUPPORTED` in the enabled build; DS2 disabled build behaves as today (unknown id with other types `BAD_PARAMETERS`, with `VALUE_OUTPUT` `NOT_SUPPORTED`); DS3 a refused legacy id is `NOT_SUPPORTED` regardless of types; DS4 init failure: 17 to 23 `BAD_STATE`, legacy 1, 2, 12 still work. All `NOT RUN`; they join the design inventory with the interface section.

### DEC-IF-3 Command 17 (DECIDED 2026-11-07, all five recommendations approved)
Parameters: exact `param_types` `(VALUE_OUTPUT, MEMREF_INPUT, VALUE_OUTPUT, VALUE_OUTPUT)`; `p0.a` verdict, `p0.b` detail; `p1` the message; `p2`/`p3` the health pair. Little-endian. Message `can_id(4) | counter(4) | payload(4) | tag(32)` = 44 bytes (the 8 padding bytes of the 48-byte CAN-FD data field on the bus are dropped by the consumer; the PTA message has none). Tag = HMAC-SHA256 over the first 12 bytes with `K_frame`, compared in constant time over all 32 bytes. `payload` is opaque.
Decisions: (3.1) a size other than 44 is verdict MALFORMED detail 1, with an event, and the buffer is not read (not `BAD_PARAMETERS`); (3.2) **no size cap**; (3.3) stream list is the compile-time constant `{0x123}` (matches `SECURE_ALLOWED_CAN_ID`); the counter state is one instance per mode, so a second id would need a per-stream state array; any other id is MALFORMED detail 3; `can_id` above `0x1FFFFFFF` is MALFORMED detail 2; (3.4) verdict codes ACCEPTED 0, GAP 1, RESYNC 2, MALFORMED 3, AUTH_FAIL 4, REPLAY 5, DUPLICATE 6, CONFLICT 7; detail is 0 except GAP (counter - last - 1) and MALFORMED (reason 1, 2, 3); (3.5) `BUSY` happens only before any state change, so a resubmission is safe and not miscounted.
Order: (1) wrong types or a NULL buffer with size above 0 is `BAD_PARAMETERS`, then `init_ok` = 0 is `BAD_STATE`; (2) length; (3) copy 44 bytes once into a local buffer before any lock; (4) `can_id` range, then stream list; (5) HMAC with the guarded `mac_pta` outside the lock (guard busy returns `BUSY`), constant-time tag compare, mismatch is AUTH_FAIL; (6) one bounded hold: evaluate, counter rules, state update, events, unlock (budget exhausted returns `BUSY`). Steps 1 to 5 change no state.
Counter rules, in this order with direct unsigned comparisons and no delta variable: no previous frame is RESYNC (any counter, including 0); `counter < last` REPLAY; `counter == last` DUPLICATE if the 44 bytes equal the stored frame, else CONFLICT; `counter == last + 1` ACCEPTED (guarded so it cannot wrap; after `0xFFFFFFFF`, counter 0 is REPLAY); `counter > last + 1` GAP. Only ACCEPTED, GAP and RESYNC refresh the traffic deadline (and clear a raised timeout). Only the last accepted frame is stored.
Known limits to keep in the report: state resets on reboot, so a captured valid frame can be accepted again as the first frame (RESYNC) after a restart; a GAP cannot tell bus loss from a drop by Linux; while a caller hammers the PTA, real frames can be refused with `BUSY` and Core 1 can raise a traffic timeout although traffic flows (F24).
Which verdicts raise which events is part of DEC-IF-10. Checks (all `NOT RUN`): C17-1 size not 44 is MALFORMED and the buffer is not read; C17-2 `can_id` range and stream list; C17-3 AUTH_FAIL changes no state; C17-4 the counter vector (last=100: 90 REPLAY, 100 DUPLICATE or CONFLICT, 101 ACCEPTED, 105 GAP of 3, `0xFFFFFFFF` then 0 REPLAY, first frame with counter 0 RESYNC); C17-5 the deadline is refreshed only by ACCEPTED, GAP and RESYNC; C17-6 `BUSY` precedes any state change; C17-7 the copy is before the lock and the HMAC outside it; C17-8 constant-time compare over 32 bytes; C17-9 NULL buffer with size above 0 is `BAD_PARAMETERS`.

### DEC-IF-4 Command 19 (DECIDED 2026-11-07, Option B: `ev_ack` is a bookmark only)
Why: the PTA cannot tell callers apart (any `/dev/tee0` user is equal), so a command that changed loss accounting would be an unauthenticated way to hide loss. A consumer detects loss from contiguous event seq numbers (a jump between the last seq read and the first seq now in the ring); rate-limited events carry no seq and exist only in the exact counters.
Decision: an acknowledgement **never** changes `ev_lost` and never changes which entry is overwritten. `ack_upto_seq` above `ev_seq` is clamped to `ev_seq`; a value below `ev_ack` is a no-op; `ev_ack` never decreases. Contract: exact `param_types` `(VALUE_INOUT, NONE, VALUE_OUTPUT, VALUE_OUTPUT)`; `p0` in `a` = ack up to seq, in `b` = 0 (non-zero is `BAD_PARAMETERS`); out `a` = verdict 0, out `b` = the **effective** `ev_ack` after clamping (not an entries-released count, which would need a ring scan for no benefit); `p2`/`p3` health pair. One bounded hold; evaluation runs first like every command. Order: types and reserved field (`BAD_PARAMETERS`), `init_ok` (`BAD_STATE`), then the hold (`BUSY` on exhaustion).
G8 wording to change in the interface edit: `ev_ack` is "a bookmark only, never affecting overwriting or `ev_lost`" (replaces "pinned entries are exempt from `ev_ack`").
Checks (all `NOT RUN`): ACK1 an acknowledgement never changes `ev_lost` or the overwrite victim; ACK2 clamp above `ev_seq`, `out b` reports the effective value; ACK3 a lower value is a no-op and `ev_ack` never decreases; ACK4 in-`b` non-zero is `BAD_PARAMETERS`, health pair filled on `SUCCESS` and `BUSY` only.

### DEC-IF-5 Command 21 (DECIDED 2026-11-07, approved as proposed)
Exact `param_types` `(VALUE_INOUT, NONE, VALUE_OUTPUT, VALUE_OUTPUT)`. In `a` = mode (0 EXPECTED, 1 IDLE; anything else `BAD_PARAMETERS`); in `b` = requested ms (mode 1 with 0, or mode 0 with non-zero, is `BAD_PARAMETERS`); out `a` = verdict; out `b` = remaining lease ms after the call (0 in EXPECTED), saturating. Order: types and reserved fields, `init_ok`, one bounded hold (`BUSY` on exhaustion); evaluation first, so a lease that just expired is already back in EXPECTED and the verdict follows the post-evaluation state.
Behaviour: IDLE while EXPECTED is GRANTED 0 (expiry `now + min(b, IDLE_MAX)` in ticks); IDLE while IDLE is RENEWED 1 (new expiry `now + min(b, IDLE_MAX)`, replacing and **not** added to the remaining time, and it may shorten the lease); at `IDLE_USES_MAX` the request is REFUSED_CAP 3 with an event and no change; EXPECTED while IDLE is RETURNED_TO_EXPECTED 2 and restarts the traffic window (G5-4); EXPECTED while EXPECTED is NO_CHANGE 4 (no event, no use). Only granted and renewed requests increment `idle_uses`; refusals and returns do not (returning to EXPECTED is free). A grant never clears an already-raised timeout (G5-6). The lease disarms the traffic deadline only; the heartbeat keeps running (G5-1). Events follow G5-2 (a grant from EXPECTED logs `LEASE_GRANTED` and `MODE_CHANGED`; whether it should be one event is part of DEC-IF-10).
Worst-case exposure from a hostile caller (unauthenticated command): blind traffic deadline of at most `IDLE_MAX` x `IDLE_USES_MAX` per boot, a refused legitimate idle request if the cap is used up, and every use visible in `idle_uses`, the remaining time (cmd 20) and the events. Values for `IDLE_MAX` and `IDLE_USES_MAX` are in DEC-IF-11 (placeholder 60,000 ms and 16 uses, worst-case blind time 16 minutes).
Checks (all `NOT RUN`): L21-1 parameter validation; L21-2 clamp and reported time; L21-3 the five verdicts in the right states; L21-4 only granted and renewed requests count, REFUSED_CAP changes nothing; L21-5 renewal is `now + clamped`, not additive; L21-6 return restarts the window and a grant does not clear a raised timeout; L21-7 heartbeat evaluation unaffected during IDLE; L21-8 a lease that expires during evaluation yields GRANTED, not RENEWED; L21-9 events follow G5-2 and exact counters survive the per-class limit.

### DEC-IF-6 Command 22 (DECIDED 2026-11-07, all four recommendations approved)
Exact `param_types` `(VALUE_OUTPUT, VALUE_OUTPUT, VALUE_OUTPUT, VALUE_OUTPUT)`; no input fields. `p0.a`/`p0.b` = nonce low and high word (the 8 nonce bytes as a little-endian 64-bit value; zero when no request is answerable); `p1.a` = `hb_seq`; `p1.b` = `hb_state` (NONE 0, OPEN 1, ANSWERED 2, MISSED 3, LATE_ANSWERED 4); `p2`/`p3` health pair.
Decisions: (1) a nonce is returned in **OPEN and MISSED**; NONE, ANSWERED and LATE_ANSWERED return a zero nonce with the state; (2) if `hb_seq` changed between the two holds the command stores nothing and returns the new `hb_seq` and state with a **zero nonce**; the caller retries, there is **no internal retry**; (3) derivation input is exactly 16 bytes, `boot_id (4, LE) || hb_seq (4, LE) || issue_ticks (8, LE)`, nonce = first 8 bytes of `HMAC-SHA256(K_hb, input)`, low word = bytes 0 to 3 LE, high word = bytes 4 to 7 LE; (4) **Core 1 is the only component that issues challenges; the PTA never issues one.**
Sequence: types (`BAD_PARAMETERS`), `init_ok` (`BAD_STATE`); hold 1 (evaluate, read `hb_seq`, `hb_state`, `hb_issue_ticks`, stored nonce and valid flag; not answerable or already stored finishes here); unlock; enter the `mac_pta` guard (busy returns `BUSY`), HMAC, leave the guard; hold 2 with the remaining budget (exhausted returns `BUSY`), store only if `hb_seq` is unchanged; copy out after unlock.
Consequences to keep in the report: until Core 1 integration exists (blocked on D1) no challenge is issued on the board, so command 22 reports NONE and command 23 reports UNISSUED there; the logic is tested on the host with a mock Core 1. The nonce is public to any process that can open `/dev/tee0`, so the heartbeat proves that some PTA-capable process answered a fresh challenge, not that the legitimate consumer is healthy. The first caller after each challenge pays the HMAC (about 3 ms per PTA call in the stacks-on build, an inference from F22).
Checks (all `NOT RUN`): N22-1 exact `param_types`, `BAD_PARAMETERS` before `BAD_STATE`; N22-2 NONE, ANSWERED and LATE_ANSWERED return a zero nonce with the state; N22-3 OPEN and MISSED return the nonce, matching a known HMAC-SHA256 vector for fixed inputs; N22-4 a second call for the same challenge does not recompute; N22-5 `hb_seq` changed between the holds stores nothing and returns the new state with a zero nonce; N22-6 the second hold uses only the remaining budget, exhaustion is `BUSY`; N22-7 guard busy returns `BUSY` before the HMAC with no state change; N22-8 the HMAC runs with the lock released; N22-9 input layout and byte order exactly as specified; N22-10 health pair filled on `SUCCESS` and `BUSY` only.

### DEC-D1 FIQ policy (DECIDED 2026-11-07, Option B)
FIQ stays masked throughout the entire Core 1 monitor loop in Monitor builds. Requirements: never unmask FIQ in the loop; a runtime assertion at loop entry; a static check that the loop never unmasks FIQ; the legacy CAN FIQ path is not enabled in Monitor mode; the non-Monitor build is unchanged. This removes the O-01 stack-overlap risk by construction. Option A (mask only around each attempt, stack reserve of 2 KB or more, on-board stack-watermark test) was rejected. See `MONITOR_STATE_DESIGN.md` section 4g C7. The change to `rpi3_can_server.c` is part of the Core 1 integration stage and is not made yet.
