## 1. Context and goal
Detect (a) forged/modified/replayed frames and traffic loss **without trusting Linux**, and (b) evidence that Linux is stalled / hiding / altering frames. Plan 1 (fallback, no chip B) = Linux forwards frames to the PTA. Plan 2 = Design 2 (above). Step 2 (verified boot, Core 1, FIQ, `secure_can_demo`, PTA cmds 0–16) must keep working. **A heartbeat success never suppresses a CAN-monitoring or report-consistency finding.**

## 3. Frozen design rules
**R1 Frame format.** Wire frame = CAN-FD, standard ID 0x123, 48 data bytes (DLC 14): `counter u32 LE (0..3) ‖ payload 4 B (4..7) ‖ tag 32 B (8..39) ‖ pad 8 B (40..47)`. Tag = HMAC-SHA256(K_frame, `id u32 LE ‖ counter u32 LE ‖ payload`) = over 12 bytes; compared in constant time over all 32 bytes. Pad is ignored and unauthenticated by design (documented). Monitor message (cmd 17, mode F) = `can_id u32 LE (masked CAN_EFF_MASK) ‖ counter ‖ payload ‖ tag` = 44 bytes; the consumer rejects EFF/RTR/ERR frames, non-FD frames and wrong lengths and passes flags in a VALUE_INPUT (flags are not under the HMAC).

**R2 Counter policy (one shared function `mon_counter_step()`, separate state per mode).** Direct unsigned comparisons, in this order, no `delta` variable: (1) no previous counter → COUNTER_RESYNC (incl. 0), `last=counter`; (2) `counter == last` → **compared over the canonical authenticated fields only (`can_id`, `counter`, `payload`, `tag` = 44 bytes; padding bytes 40..47 are excluded, so a padding-only difference produces no event at all)**: identical = DUPLICATE_FRAME (counted, rate-limited), different = COUNTER_CONFLICT. This comparison runs only **after** format, stream and HMAC checks passed (a frame with a bad tag is INVALID_AUTHENTICATION and never reaches the counter rules); the last accepted canonical 44 bytes are stored with the counter state; (3) `counter < last` → REPLAY_DETECTED (state and deadline unchanged); (4) `counter == last+1` → accept; (5) `counter > last+1` → COUNTER_GAP(skipped = counter−last−1); the authenticated frame **is accepted**, `last=counter`, deadline refreshed. Wrap out of scope (0xFFFFFFFF→0 = REPLAY). Test vector (last=100): 90→REPLAY, 100→DUP/CONFLICT, 101→accept, 105→GAP(3), 0xFFFFFFFF then 0→REPLAY. **Sender restart** (I-09): stays REPLAY/TIMEOUT until `MON_RESET` (debug) or monitor reboot — documented limit unless the professor chooses an authenticated epoch.

**R3 Traffic deadline.** Arms on the first valid frame; measured in 19.2 MHz secure ticks; source = Linux forwards (mode F) or chip B arrivals (mode D2). REPLAY/DUPLICATE/CONFLICT/MALFORMED/AUTH_FAIL do not refresh it; accept/GAP/RESYNC do. Idle mode has a lease, is capped per boot, every use is an event.

**R4 Heartbeat — see R17 (full protocol).** R4b stands: three independent verdicts, never merged: (a) liveness, (b) bus evidence (chip B verification, deadline, health), (c) report consistency. A good heartbeat never suppresses (b) or (c) and is never reported as "consumer honest"; only "something able to call the PTA answered a fresh challenge".

**R5 Report wire format (mode D2) [v3].** Little-endian. Header 16 B: `magic u16 | ver u8 | n u8 | boot_id u32 | report_seq u32 | chipA_drops u32`. Then `n ≤ 32` entries × 24 B `{ctr u32, payload 4 B, tag16 16 B}`, `tag16` = first 16 bytes of the frame's 32-byte HMAC. **Total size must equal exactly `16 + 24·n` (max 784 B)**; any other size, bad magic/ver, `n>32`, or entries not strictly increasing → REPORT_MALFORMED. Secure World revalidates each entry: HMAC over `0x123 ‖ ctr ‖ payload`, constant-time compare of the first 16 bytes. `report_seq` = the `hb_seq` the report answers. `chipA_drops` is an unauthenticated Linux claim, decreases logged as DROP_COUNTER_RESET, never excuses a missing frame without a chip B error/overflow.

**R6 Cross-check (Core 1 only).** Key `(ctr, tag16)`. Same ctr, different content → FRAME_ALTERED. Reported ctr with no record: tag valid → B_MISS (chip B gap, not a Linux fault); tag invalid → FABRICATED_REPORT. A record is **MATCHED as soon as any accepted report contains it** (at any time); its **absence** is judged only by the first accepted report that arrives at/after `t_seen + grace` (and covers it, R19). If no such report arrives the record stays unjudged — the missing report itself is already reported once per request as REPORT_TIMEOUT (R20), so the record level never logs a second REPORT_TIMEOUT — and a record evicted still unjudged → EVICTED_UNJUDGED. grace ≥ 2R + measured p99.9. **FRAME_UNACCOUNTED is a finding, not an accusation:** it means "chip B saw and verified this frame, and an accepted report whose range covers it omitted it". Benign causes that cannot be excluded: chip A or SocketCAN queue overflow, consumer restart, consumer bug; malicious omission is only one possibility. Reports and slides must word it that way, and it is never merged with COVERAGE_GAP, heartbeat or chip B events into one verdict. Eviction before judgement → EVICTED_UNJUDGED. Same direct unsigned comparisons as R2.

**R7 Diagnosis inputs:** chip B health {OK, OVERFLOW, DEAD} × traffic {Y,N} × heartbeat {Y,N} × report {NONE, PRESENT} × compare {EQ, LINUX_MISSING, EXTRA_VALID, EXTRA_INVALID, DIFF, DUP}. DEAD → CHIPB_FAULT, comparison INCONCLUSIVE, no UNACCOUNTED. No traffic never raises UNACCOUNTED. "Traffic stopped" lists four possible causes (sender stopped, chip A disabled, chip B failed, bus/ACK problem); Secure World separates only what chip B counters and retransmission patterns show.

**R8 Locking and ownership.** Mode F: PTA `cpu_spin_lock_xsave`; Core 1 bounded `cpu_spin_trylock` (verified legal on Core 1: masks nothing; Core 1 uses only `cpu_spin_*`, no thread context); FIQ handler never locks; **the clock used for any deadline decision is read inside the critical section (R21), never before acquiring the lock**; MON_STARVED after K skips. Mode D2: chip B ring has Core 1 as single writer, readers use a seqlock. HMAC outside locks; memrefs copied once with byte reads into a local buffer. Two MAC contexts (I-10).

**R9 Dispatch (verified against `core/pta/rpi3_can_spi_poc.c`).** `invoke_command` handles most commands as per-command `if (cmd_id == …)` blocks that each build their own `exp_pt` and return BAD_PARAMETERS on mismatch (lines ~209–366); the **generic check `if (param_types != exp_pt)` is at line ~372 and the `switch (cmd_id)` starts at ~375**, so a new command placed only in the switch would be rejected unless it is VALUE_OUTPUT-only. New commands ≥17 go in one `#ifdef CFG_RPI3_CAN_MONITOR` block **before** line ~372 that calls `rpi3_can_monitor_invoke()` and does its own exact `param_types` match, following the existing pattern; commands 0–16 are not edited.

**R10 Control commands.** SET_TRAFFIC_MODE, SET_D2_MODE one-way/leased/compile-time; every attempt logged; chip B health/auth monitoring never switched off. Monitor profile removes or logs debug cmds 3/6/7/13/14.

**R11 Output and bounded execution.** RAM log (pinned first-N-per-class entries, overflow marker, optional hash chain, ack cursor) + UART lines with `seq=`, token bucket, bounded length, `ALIVE seq=N poll_age=…` every 1 s. Core 1 never waits unboundedly on UART: enable `CFG_8250_UART_FLUSH_TIMEOUT` (+ small `_US`) or use an own non-blocking drain (write only if LSR.THRE set, 1–2 bytes per pass). Bounded frames per pass; no logging in the poll critical path; no printing under a lock. **Health = progress**, not loop liveness: `last_poll_ticks`/`poll_count` age → CORE1_POLL_STALL.

**R12 Keys.** `K_frame`: sender + Secure World only (consumer relays bytes, never needs it). `K_hb`: Secure World only. `K_test`: Linux test tools only. Provisioning = compiled constant in the OP-TEE image (no HUK/secure storage on Pi 3) → readable by root Linux (boot partition, `/dev/mem`); HMAC is not provenance against root Linux and does not encrypt payload. PTA has no caller authorization (any TEEC client with the UUID).

**R13 Chip A policy.** While Linux owns can0 the Step 2 chip-A path (FIQ arm, `can0_secure_init`, UINC reads) stays dormant and is refused in the Monitor profile. Chip B is Core 1's only receiver in mode D2.

**R14 Parameters (all provisional until measured):** T=50 ms, R≈500 ms, timeout=T+J+C+M, k, H, D_req, G measured; fixed 19.2 MHz constant (one-time CNTPCT sanity on Core 1; don't trust CNTFRQ). **Invariant: D_req < H.**

**R15 Event glossary [v3].** frame: MALFORMED_MESSAGE, INVALID_AUTHENTICATION(=HMAC_FAILURE), REPLAY_DETECTED, COUNTER_GAP, COUNTER_RESYNC, DUPLICATE_FRAME, COUNTER_CONFLICT · deadline: CAN_TRAFFIC_TIMEOUT, CAN_TRAFFIC_RECOVERED · heartbeat: HEARTBEAT_MISS (one request missed), HEARTBEAT_LATE, HEARTBEAT_SEQ_EXHAUSTED, CONSUMER_HEARTBEAT_TIMEOUT (k consecutive misses; =HEARTBEAT_MISS in Word report), CONSUMER_HEARTBEAT_RECOVERED, CONSUMER_NEVER_STARTED, BAD_NONCE, STALE_RESPONSE, DUPLICATE_RESPONSE, UNISSUED_CHALLENGE · report: REPORT_TIMEOUT, REPORT_MALFORMED, REPORT_DUPLICATE, REPORT_STALE, REPORT_LATE, REPORT_REPLAY(=stale boot/seq), REPORT_COVERAGE_GAP (frame outside the reported range — not an attack finding) · cross-check: FRAME_ALTERED, FRAME_UNACCOUNTED, FABRICATED_REPORT, B_MISS, OBSERVATION_GAP, EVICTED_UNJUDGED, DROP_COUNTER_RESET, CHIPB_FAULT, CONTROLLER_CONFIG_MISMATCH · monitor: MONITOR_MODE_CHANGED, MODE_CHANGE_ATTEMPT, IDLE_EXPIRED, LOG_OVERFLOW, MON_STARVED, COMM_ERROR, CORE1_POLL_STALL, UART_TIMEOUT, CONSOLE_TAMPER, GPIO_TAMPER, FIQ_STORM. **R19 Report generation, retention, overlap and overflow [v3.2].**
- *Contract for the consumer:* each report contains the **most recent up to 32 distinct frames it has handled, in strictly increasing counter order** (a rolling window, deliberately overlapping earlier reports), not just "new since the last report". With T=50 ms and R≈500 ms (≈10 new frames per report) 32 entries span ≈ 1.6 s ≈ 3 reports; **ring capacity is computed, not assumed [v3.3]:** `derive_params.py` computes `N_req = ceil((grace + R + 32·T) / T) + margin` with `margin ≥ 25 %` (documented), from the measured `grace` (= 2R + L99.9) and the nominal T, and **writes the result to a generated header `mon_params.h` that sizes `MON_RECORD_RING` (compile-time constant, `_Static_assert N_ring ≥ N_req`)**; derivation fails (build refused) if the configured ring is too small. Worked check with the provisional numbers: grace ≈ 1.1 s → (1.1 + 0.5 + 1.6)/0.05 = **64 with zero margin**, so the default ring is **128 records** (≈ 4 KB static), not 64. Records are evicted only when judged or when `age > grace + R + 32·T`; a record forced out earlier (a frame rate far above T, e.g. a flood) is counted as EVICTED_UNJUDGED (rate-limited, never silent) and the report says that a flood can blind judgement. Also asserted: `32·T ≥ grace + R`.
- *Coverage rule (Secure World):* a report covers the counter range `[min_ctr, max_ctr]` of its entries. A Core 1 record `r` (older than grace) is judged **UNACCOUNTED only if `min_ctr ≤ r.ctr ≤ max_ctr` and `r` is absent** (an omission inside the reported range). A record with `r.ctr > max_ctr` is "not yet covered" and waits for a later report; a record with `r.ctr < min_ctr` that no accepted report ever covered before its judgement time is logged **REPORT_COVERAGE_GAP** (consumer slower than the window, burst, flood, or omission-by-overflow — indistinguishable from the inside) and is **not** FRAME_UNACCOUNTED and not evidence of malice. Consequence stated openly: a hidden newest frame (above every later `max_ctr`) is undetectable.
- *More than 32 frames between reports:* the consumer sends the newest 32; frames pushed out of the window follow the coverage rule above (COVERAGE_GAP). The monitor never infers malicious omission from a full report.
- *Core 1 chip B outcome cross-over:* a counter inside the range that chip B logged as GAP/overflow (OBSERVATION_GAP) is not judged either way.

**R20 Report timing model: three separate times per request issued at `I` [v3.2].**
1. *Report due time* `I + D_rep`, `D_rep = D_req + R` (the consumer submits the report no later than its next period). Same boundary as the heartbeat: a report received at `t` with `t − I ≤ D_rep` is **on time (inclusive)**; with `t − I > D_rep` it is late. If no accepted report for `s` exists when `now − I > D_rep` (strict) → **REPORT_TIMEOUT**, logged once for `s`, by whichever of Core 1 or the PTA submit handler observes it first (under the lock).
2. *Eligibility window* `[I_s, I_{s+W})` i.e. while `current − s < W` (W=4): a delayed report is still accepted and evaluated for evidence, logged **REPORT_LATE** if `t − I > D_rep`; it never cancels the REPORT_TIMEOUT already logged. From the moment the (s+W)-th request is issued the sequence is ineligible → REPORT_STALE (rejected, not evaluated; its frames can still be judged by later overlapping reports, R19).
3. *Final state of every issued request is two independent facts, both retained until the sequence leaves the window [v3.3]:* `deadline_outcome` ∈ {PENDING, ON_TIME, TIMED_OUT} and `receipt` ∈ {NONE, ON_TIME, LATE}, with an `evaluated` flag. Transitions (all under the lock, R21): receipt at or before the deadline → `deadline_outcome = ON_TIME`, `receipt = ON_TIME`; the deadline passes with `receipt == NONE` → `deadline_outcome = TIMED_OUT`, REPORT_TIMEOUT logged once; a report arriving after that → `receipt = LATE`, REPORT_LATE logged once, the report **is evaluated** (once) and `deadline_outcome` **stays TIMED_OUT** (the timeout is never cancelled). Any further submission for the same `s` after `receipt != NONE` → REPORT_DUPLICATE (ignored, not re-evaluated, no state change). So the four possible end states are (ON_TIME, ON_TIME), (TIMED_OUT, LATE), (TIMED_OUT, NONE), and stale-rejected (outside the window, never evaluated). **Parameter assertions at derivation (one definition: `L_rep99.9` = measured 99.9th percentile of the consumer's report build-and-submit latency, used everywhere):** `D_rep + L_rep99.9 < W·H` (a merely slow report is still eligible), `32·T ≥ grace + R`, and the ring-size assertion in R19; a lost report is covered by the overlap of the following reports (T42).

**R21 Synchronization protocol (one rule set for all deadline decisions) [v3.3].**
- **One lock** (`mon_lock`) guards all monitor state **and** the event ring, so there is no lock ordering and no deadlock between locks. Critical sections contain only field reads/writes, comparisons and a fixed-size (≤ 24 B) event-ring append — **no HMAC, no UART, no memcpy of caller buffers, no allocation, no calls that can sleep.** UART text is produced after the lock is released from a copy of the event. The PTA takes it with `cpu_spin_lock_xsave`; Core 1 with a bounded `cpu_spin_trylock` (on failure Core 1 skips the pass, counts a skip, MON_STARVED after K consecutive skips; PTA handlers independently catch expiry, so a starved Core 1 cannot make a deadline pass unnoticed).
- **The clock is read inside the critical section**, after the lock is held (`now = barrier_read_counter_timer()`), by every handler and by Core 1. Reading before the lock would let a handler decide "on time" with a stale `now` after waiting for the lock — exactly the race I-19 fixes. (Core 1 may peek at the clock before the try-lock only to skip work when nothing can be due; it must re-read inside.)
- **One predicate, one helper:** `expired(now, issue_ticks, limit) := (now − issue_ticks) > limit` (strict), used by Core 1 and by both handlers; so the boundary (exactly the limit is on time) is identical everywhere.
- **Exactly-once by construction:** every miss, timeout and late event is attached to a **state transition guarded by its current value, performed under the lock**: heartbeat `OPEN→MISSED` (increments `miss_count`, logs HEARTBEAT_MISS), report `deadline_outcome PENDING→TIMED_OUT` (logs REPORT_TIMEOUT), `MISSED→LATE_ANSWERED` (HEARTBEAT_LATE), `receipt NONE→LATE` (REPORT_LATE). Whoever holds the lock second finds the state already changed and does nothing, so the answer handler and Core 1 cannot count the same miss, and the report handler and Core 1 cannot log the same timeout, twice.
- **Lazy nonce without HMAC under the lock:** lock → copy `(boot_id, hb_seq, issue_ticks, nonce_valid)` → unlock → compute HMAC → lock → store the nonce only if `hb_seq` is unchanged (compare-and-set) → unlock.
- **Bounded:** each handler holds the lock for a small constant number of operations; the worst case is measured (S2b) and recorded.

## 4. Why a successful heartbeat cannot hide findings
The three verdicts have separate state and separate events. Heartbeat OK + report MISMATCH → FRAME_ALTERED is logged. Heartbeat OK + report MISSING → REPORT_TIMEOUT. Heartbeat MISS + report OK → HEARTBEAT_MISS logged and the report is still evaluated. Heartbeat OK + chip B sees AUTH_FAIL/REPLAY → logged regardless.

## 5. Heartbeat protocol (R17) — lifecycle, ownership, rules
**State (all under the monitor lock):**
| Variable | Owner (writer) | Readers | Meaning |
|---|---|---|---|
| `boot_id u32` | monitor init (driver_init), once | PTA, Core 1 | **a uniqueness tag, not a secret:** low 32 bits of `HMAC(K_hb, init_ticks64 ‖ prng16)`. Verified in `core/tee/tee_cryp_utl.c`: the software PRNG (`CFG_WITH_SOFTWARE_PRNG=y`, Fortuna) is seeded **only from the system timestamp** ("This isn't much of a seed"); `plat-rpi3` has no hardware RNG and no override, so `prng16` adds little. Uniqueness across boots therefore rests on `init_ticks64` (time since power-on, 52 ns resolution, boot jitter) and is **tested, not assumed** (T18b). Collision across boots is improbable but not guaranteed; it is documented as a limitation. The nonce is a freshness token, not a secret: `K_hb` is readable by root Linux and the nonce is handed to Linux by cmd 22 anyway |
| `hb_seq u32` | Core 1 (issue) | PTA | 0 at boot, first request = 1; never decremented |
| `issue_ticks u64` | Core 1 | PTA | secure ticks at issue |
| `nonce u64`, `nonce_valid` | PTA (lazy, first fetch of this seq) | PTA | first 8 B of HMAC(K_hb, boot_id ‖ hb_seq ‖ issue_ticks); identical on repeated fetches |
| `state` ∈ {NONE, OPEN, ANSWERED, MISSED, LATE_ANSWERED} | Core 1: NONE/ANSWERED/MISSED/LATE_ANSWERED→OPEN (issue); **OPEN→MISSED is made exactly once, under the lock, by whichever of Core 1 or the PTA answer handler first observes `now − issue_ticks > D_req`**; PTA: OPEN→ANSWERED (on time), MISSED→LATE_ANSWERED (first late answer) | both | one outstanding request at a time |
| `rep[W]` = `{deadline_outcome, receipt, evaluated}` per request | Core 1 (PENDING→TIMED_OUT), PTA submit handler (receipt), both under the lock | both | report timeout and late receipt kept as separate facts (R20 item 3) |
| `miss_count`, `timeout_raised` | Core 1 | PTA | consecutive misses; k = threshold |
| `last_ok_ticks` | PTA | Core 1 | last on-time answer |

**Lifecycle:**
1. **Issue (Core 1, no crypto):** when `now ≥ next_issue`: `hb_seq++`, `issue_ticks = now`, `next_issue = max(issue_ticks_prev + H, now) ` for the grid, but **never a catch-up burst** (if Core 1 was stalled, exactly one request is issued and the grid restarts from `now`), state OPEN. Because the invariant D_req < H is asserted when parameters are derived (`derive_params.py` fails otherwise) and Core 1 resolves OPEN→MISSED at `issue_ticks + D_req`, the previous request is already ANSWERED or MISSED at the next issue, so nothing is silently overwritten (a defensive check logs MON_STARVED and does not overwrite if the state is still OPEN). Core 1 does this under bounded try-lock; on failure it retries on the next pass.
2. **Availability / fetch (cmd 22):** Linux consumer calls; if state OPEN, PTA computes (once) and returns `{boot_id, hb_seq, nonce}`; if no open request returns state NONE/ANSWERED/MISSED with the last `hb_seq` and the consumer waits. Fetch is idempotent.
3. **Response (cmd 23) `{boot_id, hb_seq, nonce}`**, checks in order: `boot_id` mismatch → UNISSUED_CHALLENGE (consumer must refetch); `hb_seq > current` → UNISSUED_CHALLENGE; `hb_seq < current` → STALE_RESPONSE; `hb_seq == current`, handled **under the lock after reading the secure clock `now`**: (i) if state is OPEN and `now − issue_ticks > D_req` the handler first performs the OPEN→MISSED transition itself (HEARTBEAT_MISS, `miss_count++`, exactly once — Core 1 will then find MISSED and do nothing) and continues as MISSED; (ii) state OPEN (so `now − issue_ticks ≤ D_req`; **exactly D_req is on time**) → nonce constant-time compare: equal → ANSWERED (`miss_count=0`; if `timeout_raised` → RECOVERED) else BAD_NONCE (state stays OPEN); (iii) state ANSWERED or LATE_ANSWERED → DUPLICATE_RESPONSE (state unchanged, no `miss_count` change); (iv) state MISSED → nonce must match → LATE_ANSWERED and **HEARTBEAT_LATE logged once** (liveness evidence, `miss_count` not reset); a wrong nonce → BAD_NONCE, state stays MISSED.
4. **Deadline and miss counting (Core 1, each pass):** if state is OPEN and `now − issue_ticks > D_req` (strict `>`, the same boundary as the answer handler) → state becomes MISSED **once** (unless the PTA answer handler already made the transition), HEARTBEAT_MISS is logged, `miss_count++`; at `hb_seq == 0xFFFFFFFF` Core 1 stops issuing and logs HEARTBEAT_SEQ_EXHAUSTED once (no wraparound; ~68 years at H=500 ms). `miss_count` = number of **consecutive** requests that resolved MISSED with no on-time answer in between; an on-time answer (step 3) sets it to 0; a late answer does **not** reset it. When `miss_count == k` and the boot grace G has elapsed → CONSUMER_HEARTBEAT_TIMEOUT, raised once (`timeout_raised`), cleared by the first on-time answer (CONSUMER_HEARTBEAT_RECOVERED). During G misses are logged but TIMEOUT is not raised; if no answer was ever accepted by G → CONSUMER_NEVER_STARTED once. `D_req = P + L99.9 + M` where P = the consumer's fetch interval (contract: P ≤ H/4), L99.9 = measured PTA-call + Core 1 check latency, M = margin; the loop pass time C only adds detection latency.
5. **Consumer restart:** consumer keeps no protocol state; next fetch returns the current request; a request already answered by the dead instance stays ANSWERED.
6. **Monitor restart / reboot:** all state lost; `boot_id` changes; consumer's cached values are rejected (UNISSUED_CHALLENGE) and it refetches; an answer or report from an old boot is rejected unless `boot_id` collides (see §14: answers additionally need the nonce, which also contains `issue_ticks`). Counter state RESYNCs on the first frame (known replay window after reboot, documented).
7. **Duplicate/replayed response:** DUPLICATE_RESPONSE / STALE_RESPONSE; no state change. **Concurrent requests:** impossible (one outstanding; PTA serialised; transitions under the lock).
8. **Report association (mode D2):** report carries `{boot_id, report_seq=hb_seq}` (R5). **Eligibility window (W=4) is counted in `hb_seq` values, not in outstanding requests:** a report for sequence `s` is eligible iff `boot_id` matches **and** `s ≥ 1` **and** `s ≤ current` **and** `current − s < W` (the subtraction is evaluated only after `s ≤ current` is known, so it cannot underflow; at startup with `current = 1` only `s = 1` is eligible, with `current = 2` only 1 and 2, etc.) **and** it is the first accepted report for `s` (a 4-bit bitmap indexed by `current − s`, shifted at every issue). `s > current` or wrong `boot_id` → UNISSUED_CHALLENGE (not evaluated); `current − s ≥ 4` → REPORT_STALE (rejected); already reported → REPORT_DUPLICATE. A sequence becomes ineligible when three further requests have been issued (≈ 3H after its own issue time; W·H must exceed D_req + report latency + R, checked at parameter derivation). Timing outcomes (REPORT_LATE / REPORT_TIMEOUT) are defined **only** by R20 (`REPORT_LATE` means "received after `I + D_rep`", not "s < current"). A report may arrive before or after the answer. The submit handler reads the secure clock itself under the lock: if `now − I > D_rep` and no report for `s` was accepted yet it logs REPORT_TIMEOUT once (so a late submit cannot slip in before Core 1's own timeout check) and then treats the report as late; each of the last W requests keeps the two fields `deadline_outcome` and `receipt` (R20 item 3), written under the lock by Core 1 (timeout) or the PTA (receipt). Heartbeat OK + report missing → REPORT_TIMEOUT only. Report present + heartbeat missing → report evaluated, HEARTBEAT_MISS logged.
9. **Timing contract:** the consumer polls (fetch) at least every `P ≤ H/4`; `D_req = P + L99.9 + M` (measured), must be `< H`. Clocks: all deadlines on the secure clock; Linux clocks are never compared.
