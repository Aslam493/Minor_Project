## Open points that need the user
1. **Define R, grace and N_req** (rules b, c). Two findings already: with grace = the 60 s boot grace G the rule `32T >= 1.25 (grace + R)` cannot hold for any R >= 0 (32T = 9.6 s); and if N_req is the plan's "default 128 records", the implemented ring (24 pinned + 40 ordinary = 64 slots, approved as G8) fails it.
2. A CAN sender or a second board for the floods and the gap histogram.
3. Accept the `CFG_RPI3_CAN_LOOP_STATS` deviation (existing TEST_STATS build used instead).

## Gate wording (plan status board, C4): "Measured T, R, H, D_req, G, ring size; CNTPCT sane on Core 1"
Honest state on 2026-11-09: **the C4 gate is NOT met.** CNTPCT sanity is met (C4.5). T (300 ms), H (1000 ms), D_req (500 ms) and G (60 s) are chosen constants, checked against the measured latencies by relations d1-d7 in `derive_params.py` (they pass), but they are not themselves "measured" values; the plan gives no definition of R; the ring is 64 slots against an undefined N_req (plan default 128). Closing the gate needs: definitions of R, grace and N_req; a decision on 64 vs 128 slots; and the flood / gap-histogram measurements, which need a CAN sender or a second board.
