## Root-cause check 3d: `speedprobe` test TA (RAM only, no flash), written before the run
A user-mode Trusted Application (S-EL0) that times, with `TEE_GetSystemTime` over loops long enough for 1 % accuracy: (A) a register-only loop (no memory access), (B) a streaming sum over 16 KiB (fits the L1 data cache), (C) the same over 256 KiB (L2), (D) 2000 calls of `TEE_GetSystemTime` (a cheap system call into the core: call overhead), (E) 50 HMAC-SHA256 of 12 bytes through the TEE API (`TEE_MACInit` + `TEE_MACComputeFinal`), (F) 50 SHA-256 of 64 bytes.
Expected on a Cortex-A53 at 1.2 GHz with caches on: (A) 2,000,000 iterations in about 8-15 ms; (B) 200 passes of 2048 words in about 1-3 ms; (C) 20 passes of 32768 words in about 3-8 ms; (D) about 2000 x (1-3 us); (E) 50 HMACs in about 1-3 ms.
Hypotheses: H1 secure memory uncached or caches off: (A) and (B) 30-100x slower than expected; H2 only data accesses uncached: (A) normal, (B) and (C) slow; H3 the secure world is throttled by clock only: all about 2x slower than expected, not 30-100x; H4 the cost is in the core crypto/syscall path only: (A)-(C) normal, (D)-(F) slow.

## Prediction for the heartbeat trace (`--hblog`), written before the runs
Facts already in the data (13+6+6 runs): every LATE_ANSWER event is raised 0.5-0.6 s after the run's start snapshot, i.e. when the forwarder starts, 4 s BEFORE the burst (4.4-4.7 s); one exception at 23.3 s (a packet-request answer, the harness status snapshot). `detail 0` = heartbeat answer (command 23), `detail 1` = packet-request answer (command 31). The Secure World calls a heartbeat answer late only if now - hb_issue_ticks > D_REQ (500 ms); the request is OPEN for 500 ms of every 1000 ms (H) and MISSED for the other 500 ms; the packet request is OPEN 40 ms of every 50 ms.
**Hypothesis H-restart:** the first answer after a forwarder (re)start is late when the start falls in the MISSED half of the heartbeat period (about 50 %) and the first packet answer is late when it falls in the 10 ms MISSED part (about 20 %). The earlier "0 of 6 without a burst" came from a locked phase (the 6 no-burst runs started exactly 49 s apart, a whole number of heartbeat periods), not from the absence of a burst. My conclusion "the burst is needed" in the previous record is therefore WITHDRAWN as unproven. User's guess (stale event kept by the ev_lost/ack bug): the events have ticks inside the run window and appear as new events after the start snapshot, so they are not stale (to be confirmed per run with the numbers below).
**Test:** 12 bursts + 8 no-burst runs, forwarder restart phase RANDOMISED (random 0-1 s wait before each run), same forwarder and settings plus `--hblog`. Per run the log gives, for every heartbeat: first-sight time of the new request number (CLOCK_MONOTONIC and CNTVCT), time the answer was sent, the verdict.
Predictions: (1) late heartbeat answer in about 35-65 % of ALL runs, with and without a burst, no difference between them; (2) in every late case the first heartbeat poll after the forwarder start returns state MISSED (3) and the verdict of that first answer is LATE; in every other run the first state is OPEN (1) and ON_TIME; (3) all later heartbeats (about 35 per run, including the ones issued during the burst at 4.4-4.7 s): first seen within 50 ms (+ call time) of their issue and answered within 1 ms, verdict ON_TIME, 0 polls with a TEEC error, 0 polls that return state OPEN/MISSED with a zero nonce; (4) CNTVCT minus the Secure World clock in the start check: within 1 ms (same reference time); (5) the packet-request LATE_ANSWER (detail 1) in about 10-30 % of all runs, also at the start.
**What refutes it:** a late heartbeat answer whose first sight comes more than about 100 ms after the request began (a delayed nonce = trylock/BUSY window), a late answer at a time inside or near the burst, a difference in rate between burst and no-burst runs outside what 20 runs can show, or a clock offset above 1 ms. In that case the previous suspicion (nonce visible late during the burst) stands and no Secure World change is proposed before it is proven.
